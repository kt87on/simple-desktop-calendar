### 1.3 重点澄清：2023 年 6 月 CA/B 新规 + 2024 年 EV/SmartScreen 变化（**已查证，务必按此更新认知**）

**(1) 2023-06-01 CA/B Forum 新规——私钥必须硬件化**
自 2023 年 6 月 1 日起，**所有**代码签名证书（OV 与 EV 一视同仁）的私钥必须生成并保存在 **FIPS 140-2 Level 2+ 或 Common Criteria EAL 4+** 的硬件模块中（USB token / HSM / 云 HSM），**私钥不可导出**。
→ 影响：**新证书不再能拿到可导出的 `.pfx` 软文件**。传统「把 pfx 丢进 CI」的做法对新证书失效；要么用 CA 邮寄的 USB token（在多台构建机之间传递很麻烦），要么用 HSM / 云签名。来源：CA/B Forum Baseline Requirements（多份 CA/微软文档一致确认）；GlobalSign 明确「2023-06-01 起 OV/EV 均须在物理保护设备上签发」。

**(2) 有效期缩短**
新签发代码签名证书有效期**上限约 460 天**（自 2025-06-15 起强制），此后进一步收紧到约 458 天（2026 年起）。→ 实际上就是**年年续**。来源：GlobalSign / CA/B Forum。

**(3) ⚠️ 2024 年 EV 不再「立即获得 SmartScreen 信誉」（最关键纠偏）**
多年来的教科书说法是「EV 签名 = 立即获得 SmartScreen 信誉，用户永不见警告；OV 要慢慢攒信誉」。**这个说法已过时。** Microsoft 官方文档《Code signing options for Windows app developers》原文：
- EV 证书**不再**默认产生正向 SmartScreen 信誉 —— **该行为「已不存在（no longer exists）」**；
- **EV 签名的文件现在和 OV 一样走「信誉积累」流程**；
- 「**仅为绕开 SmartScreen 警告而支付 EV 溢价（$400+/年）已不再合理**」。

→ 结论：**EV 的正当用途只剩两个**：① Windows 内核态驱动签名（微软硬件开发者门户强制 EV）；② 企业采购/合规硬性要求。对本项目（普通桌面应用、个人分发）**没有理由买 EV**。

**(4) 信誉绑定在「证书指纹」上**
换证/续期 → 指纹变化 → **信誉从零重建**，续期后警告可能「回魂」。缓解做法：新旧证书**重叠期双签**（dual-sign），让新证书先攒信誉。（Azure Trusted Signing 因身份固定 + 短证书自动续期，天然规避此问题。）

**(5) 题外但重要：Smart App Control（Win11 22H2+）**
SAC 比 SmartScreen 更严 —— **直接阻止**无有效可信签名的程序、**不提供「仍要运行」**。SAC 开启时接管并关闭 SmartScreen。这意味着**签名从「加分项」变成了「在启用 SAC 的 Win11 上能否运行的门槛」**（推测：对本项目新用户占比不低）。这进一步提高了「至少拿一个有效 OV 级签名」的优先级。

### 1.4 各路径申请流程（可执行到「点哪个按钮」）

**A. SignPath Foundation（推荐首选）**
1. 打开 `https://signpath.org/` → 点 **「Apply for Free Code Signing」**，填写：仓库 URL（`https://github.com/kt87on/simple-desktop-calendar`）、下载页 URL（GitHub Releases）、项目功能描述。
2. 审核（资格：OSS 许可证 MIT ✅、公开仓库 ✅、**已有发布历史**（v3.0.0 发布后满足）、功能有文档、遵守其行为准则）→ 通常数天到数周。
3. 通过后登录 **SignPath.io**：建 Organization → 建 **Artifact Configuration**（描述要签的 `.exe` / `.dll`，如 `SimpleCalendar.exe`、`SimpleCalendar-Setup-*.exe`）。
4. 接入签名：因本项目目前是**本地手动 `npm run build`**、无 CI，需要新增一条 **GitHub Actions** 工作流，用 SignPath 官方 Action 把构建产物提交去签（或按 SignPath 文档用其「手动上传」流程）。
> 关键前置：**先把 v3.0.0 Release 发出去**，满足「已有发布历史」资格。

**B. 传统 OV / IV 证书（若一定要自己署名）**
1. 选 CA（SSL.com / Sectigo / GlobalSign / DigiCert 及其授权经销商）。**个人开发者**通常只能签 **IV（Individual Validation，约 $249/年）** 或部分 CA 的 OV；OV 一般要求**有注册企业主体**。
2. 生成 CSR（**在硬件 token 上**）→ 提交营业执照/身份证明/电话核验。
3. 1–5 个工作日验证 → 证书下发到 **USB token**（邮寄，含一次性运费 $50–100）或云 HSM。
4. 配置 electron-builder：token 场景用 `certificateSubjectName`（见 1.5）。

**C. EV 证书**：流程同 B 但验证更严（1–2 周）。**本方案不推荐**（见 1.3）。

**D. Azure Trusted Signing**：`https://azure.microsoft.com/products/trusted-signing` → 创建账号（选 **$9.99/月 Basic**）→ 先授「Trusted Signing Certificate Profile Signer」与「Identity Verifier」角色 → 「Identity Validation」选 Individual/Organization 走身份核验 → 建 Certificate Profile → 用 SignTool + dlib 或 GitHub Action 签名。
**但本项目排除**：中国主体不在支持范围 + 需升级打包工具。

**E. 自签名（仅内网/开发）**：
```powershell
# 生成自签名代码签名证书（本机测试/内网用，公开分发无效）
New-SelfSignedCertificate -Type CodeSigningCert -Subject "CN=YG" `
  -CertStoreLocation Cert:\CurrentUser\My -KeyUsage DigitalSignature `
  -TextExtension @("2.5.29.37={text}1.3.6.1.5.5.7.3.3")
```
导出 `.pfx` 后在 `package.json` 配 `win.certificateFile` / `win.certificatePassword`；用户侧需手动把该证书导入「受信任的根证书颁发机构」才不告警。

### 1.5 electron-builder 配置键（**区分版本，以本机安装版本为准**）

> **本机为 electron-builder 24.13.3**。配置键随版本变化较大，务必按版本对号入座（已查证：`node_modules/app-builder-lib/out/options/winOptions.d.ts` 与 `scheme.json`）。

| 版本 | 签名配置写法 | 说明 |
|------|-------------|------|
| **24.x（本项目当前）** | **扁平键，直接写在 `win` 下**：`win.certificateFile` / `win.certificatePassword` / `win.certificateSubjectName` / `win.certificateSha1` / `win.sign`（自定义函数）/ `win.signingHashAlgorithms` / `win.publisherName` / `win.timeStampServer` / `win.rfc3161TimeStampServer` / `win.additionalCertificateFile` / `win.verifyUpdateCodeSignature` | 已核对 `winOptions.d.ts`。**没有** `signtoolOptions`、**没有** `azureSignOptions`。 |
| **26.x** | `win.signtoolOptions { certificateFile, certificatePassword, ... }` 或 `win.azureSignOptions { ... }` | 26 版才把键收进 `signtoolOptions`/`azureSignOptions`。 |
| **27.x（最新）** | 合并为单一 `win.sign` 联合类型：`{ type: "signtool" \| "hsm" \| "pkcs11" \| "azure", ... }`；`false/null` 关闭签名 | 全新 API。 |

**本项目（24.13.3）的两种落地写法：**

方案 B（PFX 文件，**仅适用于 2023 前签发的旧证书 / 自签名证书**）：
```jsonc
// package.json → build.win
"win": {
  "target": ["nsis"],
  "icon": "icon.ico",
  "requestedExecutionLevel": "asInvoker",
  "certificateFile": "cert.pfx",
  "certificatePassword": "******",
  "publisherName": "你的证书 CN",
  "signingHashAlgorithms": ["sha256"],
  "timeStampServer": "http://timestamp.digicert.com"
}
```
> 推荐把口令放环境变量而非明文：`WIN_CSC_LINK`（证书路径或 base64）+ `WIN_CSC_KEY_PASSWORD`，electron-builder 会自动发现，无需写进 `package.json`。

方案 B'（**EV / 硬件 token，无法导出 pfx**）——按「issued to」名称找证书，且**必须在 Windows 上构建**：
```jsonc
"win": {
  "certificateSubjectName": "My Company, Inc.",   // 证书 Subject 里的 CN
  "signingHashAlgorithms": ["sha256"],
  "timeStampServer": "http://timestamp.digicert.com"
}
```
> 注意：`certificateSubjectName` / `certificateSha1` 走 **Windows 证书存储**，因此只能在 Windows（或 Parallels 里的 Win10 VM）构建；纯文件签名（`certificateFile`）才可在 mac/Linux 上签。

方案 A（SignPath）：不进 `package.json`；构建后把产物交给 SignPath 的 CI Action 签名并重新产出发布物（`package.json` 保持**不加任何签名键**）。

> **务实提醒**：因 24.13.3 无 `azureSignOptions`，若哪天真要走 Azure，需把 electron-builder 升到 ≥26（牵动打包链路回归，成本另计）。结合「中国主体不可用」，Azure 路线直接排除。

## 4. 内存占用指标的对外呈现

### 4.1 现有 `tools/mem-baseline.js` 能测什么（**已 Read 源码**）

- **能力**：以 Electron 入口脚本方式加载，把产品主进程**完整启动**（不改源码、只重定向 userData 到隔离目录），在 **idle（静置 30s）/ expanded（展开）/ dock（挂件条）** 三场景下采样，输出 `REPORT.md`。
- **三个数据源**：① 进程级 `app.getAppMetrics()`（main/GPU/Renderer/Utility 分进程 WorkingSet / PeakWorkingSet / CPU%）；② 渲染层 `performance.memory.usedJSHeapSize`（V8 堆）；③ PowerShell CIM 按「本进程 + 子孙」闭包汇总（天然剔除无关/僵尸实例）。
- **诚实前提（源码与报告都写明）**：脚本**默认只能测 dev 版**，因为打包版（asar）**无法外挂入口脚本**去调用 `app.getAppMetrics()`；且 dev 版主进程名是 `electron.exe`，与机器上其它 Electron 应用同名，会产生「同名总数」噪声（报告用「本进程树进程数」规避）。
- `--disable-gpu` 收益已由同脚本量化（见 4.3）。

### 4.2 真实、可信的呈现方式

> **核心原则（已由团队实测报告确立）**：**引用内存数字必须同时注明「口径 + 运行时长 + 是否打包版」，禁止用单一数字代表日常占用。**

**（A）实测数字（均为只读采样，未经任何源码修改）**

| 形态 | 内存合计 WorkingSet | 口径 / 来源 |
|------|-------------------|-----------|
| **打包版 · 长期待机** | **≈ 163 MB** | 用户真实在跑的生产实例（`live-probe2.txt`），长期 idle，OS 已回收；分解 = main 87.8 + GPU 39.5 + utility 3.5 + renderer 9.3 + renderer 23.4 |
| dev · 冷启 30s | ≈ 405 MB（5 进程） | `.tmp-diag/mem/REPORT.md`，**含启动期临时渲染进程 / 未 trim**，会随时间回落 |
| dev · 长期 idle（+5min） | ≈ 413 MB | 同上，短时静置未见明显 trim |
| dev · 展开日历峰值 | ≈ 556 MB（峰值 593） | 同上，含 GPU 缓存峰值 |
| dev · 挂件条 | ≈ 451 MB | 同上 |
| 主进程 V8 堆 | ≈ 5–6 MB | 同上（业务逻辑本身极轻） |

**（B）对外呈现建议**

1. **README 增一张「性能与资源」小表**，只放**打包版长期待机 ≈150–165 MB** 一个主数字，并**紧跟一行口径脚注**：「5 个进程合计 WorkingSet；打包版长期待机、系统已回收缓存；冷启动前 30 秒会更高，属正常现象」。**不要把 400+/556MB 这些 dev 数字放到对外宣传里**（它们是开发态噪声，会误导用户）。
2. **About 弹窗不写内存数字**（避免被截图断章取义），只放版本/版权/链接；内存指标放 README / 使用说明。
3. **使用说明.html** 增一小节「内存与性能」，用通俗话解释口径（见 4.3）。
4. **补一次打包版分场景实测**（用 `mem-baseline.js` 的思路，对已安装的 `SimpleCalendar.exe` 做 idle/expanded/dock 三场景采样）→ 得到一组**可对外引用的官方数字**，替换现在的 dev 数字。**这是 v3.1 的建议动作**（现有脚本默认测 dev，需小幅扩展或写一个针对打包版的采样子集）。

### 4.3 如何诚实解释「Electron 内存偏高」+ `--disable-gpu` 取舍

**（1）向用户解释「为什么一个日历也占一两百 MB」——三句话：**
- Electron 是**多进程架构**：一个主进程 + 一个 GPU 进程 + 若干渲染进程 + 网络子进程，**每个进程各有一份 V8 运行时开销**，这是架构成本，不是「泄露」。
- **不同时点差别很大**：冷启动 30 秒内页面/GPU 缓存未回收会偏高，随长时间待机由 OS 逐步回收；**只盯某一刻的单个进程会误判**。
- **对比要同口径**：拿「本应用长期待机」和「别的应用冷启动」比毫无意义。

**（2）`--disable-gpu` 的真实取舍（**已由团队专项实测，数据来自 `.tmp-diag/gpu-off/REPORT.md`**）：**

| 场景 | 默认（GPU 开） | `--disable-gpu` | 节省 |
|------|---------------|-----------------|------|
| idle | 498.1 MB | 462.1 MB | **−36 MB（7.2%）** |
| expanded | 647.3 MB | 523.1 MB | **−124 MB（19.2%）** |
| dock | 598.6 MB | 535.1 MB | **−63.5 MB（10.6%）** |

- **省在哪**：几乎全部来自 **GPU 进程**（idle −44、expanded −156 MB）。
- **代价**：① **GPU 进程不会消失**（Chromium 仍保留软件合成的 GPU 进程，只是 WS 从 118.8→74.6 MB）——「关 GPU 就没 GPU 进程」是误解；② 玻璃拟态 `backdrop-filter` **仍生效**，但**模糊保真度下降**（探针块 stddev 0.56→2.6，出现轻微残留条纹）；③ 丢硬件加速 → 滚动/动画/大图渲染走 CPU，8GB 机器上可能变卡。
- **决策（团队已定，保留）**：**v3.0.0 不默认关闭**；未来可作为**「省内存模式」可选开关（默认关）** + 提示「玻璃效果可能略降级、动画流畅度下降」。
- **对外口径建议**：README 里**只客观陈述可选项的收益与代价**，不包装成「我们的软件很省内存」；并在使用说明里点明「**换掉玻璃拟态这类重模糊风格，GPU 峰值本身就会大幅下降**」——这是比关 GPU 更划算、不牺牲流畅度的方向。
