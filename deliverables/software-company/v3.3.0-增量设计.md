## §1 已查明事实（读源码得出，附行号）

### 1.1 R3 的根因（**已确证，非推测**）

`electron-main.js:866-875` 的 `materializeFromCalendar()`（`applySkinSet` 的内部函数）：

```js
c.style = cal.style;
c.bg = cal.bg;                                        // ← 把「用图片」也继承过来
c.image = cal.image ? JSON.parse(JSON.stringify(cal.image)) : null;   // ← 图片引用被复制
```

它被两个入口调用：
- `applySkinSet` 的 C2「手调即豁免跟随」分支（`:884-887`）：跟随中的面被改任一实质字段时先物化；
- `field === 'follow'` 且值为非 `'calendar'` 时（`:901-910`）：**用户把跟随开关关掉**。

而 `skincustom.html:623-625` 的 `renderCrop()` 读的是**本面自己的配置**：

```js
var cfg = getConfig(S.surface);
var img = (cfg.bg === 'image' && cfg.image) ? cfg.image : null;
```

两者叠加 → 关掉跟随 = 物化出日历的图片 = 图片框里出现主界面的图。**这就是用户看到的现象。**

### 1.2 dock 窗口尺寸是被主进程锁死的

- `electron-main.js:1113` `const DOCK_W = 116, DOCK_H = 50;`
- `:1129-1130` `let dockW = DOCK_W; let dockH = DOCK_H;` —— v1.7.22.7 起是**唯一真值**，所有布局/夹取都必须用它，**严禁用 `dockWin.getBounds()` 参与计算**（`:1114-1128` 注释有完整取证）。
- `:2602-2604` `createDock()`：`dockH = Math.max(40, Math.min(taskbarHeight(), 56)); dockW = DOCK_W;`
- `:2587-2596` `pushDockSize()` 下发 `{w: dockW, h: dockH}`；
- `:2553-2570` `positionDock()` 默认落点 = 工作区右下、压任务栏上沿；
- `:87-98` `loadSettings` 对 `dockBounds` 做尺寸校验：`Math.abs(bw - DOCK_W) <= 4 && bh in [36,60]`，不符则丢弃。
- `dock.html:546-564` `applyDockSize()`：按 `padL/T=2, padR/B=0` 摆卡片（v1.7.22.4 硬约束：右下归零才能贴死任务栏）；`:702-704` `dockLayoutSkin` 里 **`var vp = { w: 116, h: 50 }` 是写死的**。

→ 结论：方/竖造型装不进 116×任务栏高，**必须让尺寸随造型变**，连带改上述 5 处。

## §2 冻结契约

### C1 · 造型注册表（主进程 `electron-main.js` 顶层唯一真源）

```js
/* v3.3.0 浮窗造型注册表：尺寸一律以「窗口尺寸 + 四边内边距」表达，
 * 卡片尺寸由两侧各自用同一条减法算出（win - pad），杜绝两处各写一套尺寸而漂移。
 * hMode:'taskbar' → 高度跟随任务栏（clamp 40~56，沿用 createDock 既有算法）；
 * hMode:'fixed'   → 高度即注册值。
 * 非 rect 造型一律 12px 四周对称内边距 —— 它们会离开任务栏变成桌面挂件，
 * 需要给自己留出投影空间（rect 贴任务栏，右下必须 0，见 dock.html 文件头硬约束）。 */
var DOCK_SHAPES = {
  rect:    { name: '圆角卡片', winW: 116, winH: 0,   hMode: 'taskbar', padL: 2,  padT: 2,  padR: 0,  padB: 0  },
  pixel:   { name: '像素方屏', winW: 180, winH: 88,  hMode: 'fixed',   padL: 12, padT: 12, padR: 12, padB: 12 },
  rainbow: { name: '虹彩流光', winW: 140, winH: 68,  hMode: 'fixed',   padL: 12, padT: 12, padR: 12, padB: 12 },
  ring:    { name: '极简圆环', winW: 174, winH: 174, hMode: 'fixed',   padL: 12, padT: 12, padR: 12, padB: 12 },
  flip:    { name: '翻页时牌', winW: 220, winH: 128, hMode: 'fixed',   padL: 12, padT: 12, padR: 12, padB: 12 },
  toon:    { name: '绘本台钟', winW: 182, winH: 198, hMode: 'fixed',   padL: 12, padT: 12, padR: 12, padB: 12 }
};
var DOCK_SHAPE_KEYS = ['rect', 'pixel', 'rainbow', 'ring', 'flip', 'toon'];

function normShape(v)                  // 白名单外（含 undefined/null/''/'RECT'/123/{}/[]）→ 'rect'
function dockGeometry(shapeKey)        // → { key, name, winW, winH, padL, padT, padR, padB, cardW, cardH }
```

卡片尺寸换算（**两侧同一条公式**）：

```
cardW = winW - padL - padR
cardH = winH - padT - padB          // rect 的 winH 先按 hMode 求实高
```

据此，六款卡片尺寸为：rect `114×(dockH-2)`、pixel `156×64`、rainbow `116×44`、ring `150×150`、flip `196×104`、toon `158×174`。

> **rect 的 cardW 是 114 不是 116** —— 现状即如此（窗口 116、卡片左缩进 2）。注册表里 `winW:116` 是窗口宽，**不要**"顺手修正"成 118。

### C2 · 数据模型新增 `shape`

- `skin.surfaces.{calendar,expanded,desktop,dock}.shape`，取值 ∈ `DOCK_SHAPE_KEYS`，非法 → `'rect'`。
- **只有 `dock` 面可持有非 `rect` 的 shape**：`normalizeSurfaceV3` / `migrateSkinV2toV3` / `normalizeSkinV3` 对 `calendar`/`expanded`/`desktop` 一律写 `'rect'`（脏数据护栏，保证「跟随 → 拿到日历配置 → shape='rect'」这条链恒成立）。
- 旧数据（v3.2.x 及更早）无 `shape` 字段 → 补 `'rect'`。
- `shape` **纳入 `followableFields`**（手调即豁免跟随）。
- `materializeFromCalendar` **不复制 `shape`**（见 C4）。

### C3 · 跟随语义（不变）与造型的关系

- `resolveSurfaceConfig(surface)` **不改**：`follow === 'calendar'` → 返回 `skin.surfaces.calendar`（其 shape 恒为 `'rect'`）。
- 推论（写进注释）：**浮窗若在跟随态，渲染的一定是 rect**。所以「选了一款特殊造型」必然伴随 `follow` 被 C2 置 `null` —— 这正是用户说的「不跟主界面就是现在这种，跟主界面就统一」。
- `resolvedSurfaceState(surface)` 增加一个字段：`shape: c.shape`。

### C4 · `materializeFromCalendar` 不再继承图片、不继承造型（**R3 的修复本体**）

```js
function materializeFromCalendar() {
  var cal = skin.surfaces.calendar;
  c.follow = null;
  c.style = cal.style;
  /* ← 唯一的实质行为改动在这里：
   *   v3.2.x：c.bg = cal.bg; c.image = 深拷贝(cal.image)
   *   v3.3.0：背景来源与图片**都不继承**，本面回落到原生皮肤。
   *   为什么：图片是「用户自己挑的内容」，不是样式属性。跟随态的图片由日历提供；
   *   一旦取消跟随，本面就应当回到「还没选图」的空白态 —— 否则用户会看到一张
   *   不是自己选的图，误以为已经设置过（v3.3.0 用户报告的正是这个现象）。
   *   注意不是删文件：盘上 userData/skins/* 原样保留，用户随时能重新选回。
   * 背景来源必须一起回落：bg='image' + image=null 会走 solidFallbackFor 变成一块
   * 纯色兜底，那不是"回到原生皮肤"，是"变成一块灰板"。 */
  c.bg = 'native';
  c.image = null;
  c.text = cal.text;
  c.clarity = cal.clarity;
  c.tone = cal.tone;
  /* shape 刻意不复制：造型是浮窗自己的身份，不是日历的派生属性。
   * 复制会让「选过绘本台钟 → 开跟随 → 再关跟随」把台钟弄丢。 */
}
```

### C5 · 窗口几何随造型同步（主进程）

- 新增顶层函数 `syncDockGeometry()`：
  1. `var sh = normShape(resolveSurfaceConfig('dock').shape);`（注意是 **resolve 之后**的，跟随态自然得到 `'rect'`）
  2. 更新 `dockW/dockH = geometry.winW / winH`
  3. 若 `dockWin` 存在且当前 bounds 宽高与目标不符 → `dockWin.setBounds(dockClamped(curX, curY))` + `pushDockSize()`
- **调用点（三处，缺一不可）**：
  - `createDock()` 内，替代现在写死的 `dockH=...; dockW=DOCK_W;`（顺序：算好尺寸再 new BrowserWindow）
  - `applySkinSet()` 末尾，**在 `pushSkinToAll()` 之前**（保证尺寸先于皮肤样式到达渲染层）
  - `applyNativeStyleAll()` 末尾，同样在 `pushSkinToAll()` 之前
- `pushDockSize()` 载荷扩展为 `{ w, h, padL, padT, padR, padB }`（w/h = 窗口尺寸）。**保留 w/h 两个键**（`dock.html:546` 与既有断言都读它）。

### C6 · 落点策略

- `rect`（贴任务栏）：`positionDock()` **保持现状**（工作区右下、压任务栏上沿、右边距 0）。
- 非 `rect`（自由挂件）：默认落点 = 工作区右下**内缩 24px**（不压任务栏 —— 它是桌面挂件，不是任务栏附属）。实现为 `positionDock()` 内按 anchor 分支。
- `loadSettings` 的 `dockBounds` 校验（`:87-98`）改为与「**当前生效造型**的期望窗口尺寸」比对：`Math.abs(bw - geo.winW) <= 8 && Math.abs(bh - geo.winH) <= 8`，不符 → 丢弃（回落默认落点）并记日志。**删掉原来的 `[DOCK_W±4]×[36,60]` 硬编码**。

### C7 · `dock.html` 六套造型

**C7.1 属性与状态**

- `<html>` 增加 `data-shape="rect|pixel|rainbow|ring|flip|toon"`。
- 非 `rect` 时 **不写 `data-style` / `data-skin` / 不启用可读性层**：
  - 造型自带材质，皮肤与风格的 token 一律让位（跳过 `dockApplyTone` 的 style 写入、跳过 `dataset.skin`、调用 `dockClearReadability(root)`，并清掉 `#skinImg` 的背景）。
  - 这样 tech 的 `clip-path`（要求 `[data-style="tech"]`）与 `data-skin` 那批规则**自然不命中**，无需改它们的特异性。
- `rect` 时恢复现有全部行为（`data-style`/`data-skin`/`#skinImg`/`#dockTime`/`#dockDate`），**逐字保持现状**。

**C7.2 基础描边/底色/圆角/阴影 → 变量下沉**

把 `dock.html` 的 `#card` 基础规则与 hover 规则改成消费变量（**缺省值就是原值，rect 行为零变化**）：

```css
#card {
```

| shape | `--dock-bg` | `--dock-edge` | `--dock-shadow` | `--dock-radius` | `--dock-blur` / `--dock-sat` | `--dock-overflow` |
|---|---|---|---|---|---|---|

| `rainbow` | 半透明白洗（`.wg.rb` 的 background） | `transparent` | 见工装（inset 描边即 --dock-shadow） | `13px` | 由 `backdrop-filter` 规则给 `9px` / `1.3` | `hidden` |

> `flip` / `toon` 的卡片盒完全不可见，视觉全由内层承担 —— 这也是它们不能用 `overflow:hidden` 的原因

| `rect` 114×(dockH-2) | 现状 `HH:MM:SS` + `周X MM/DD` | 现状 |

- 指针角度：`hour = (h%12)*30 + m*0.5`、`min = m*6 + s*0.1`、`sec = s*6`。
- 点阵字模沿用预览工装的 `PF`（3×5）+ `PX_CELL 3.2 / PX_GAP 1.3`，**必须放进 dock.html 内联**（产物不许有外部依赖）。
- 仍然只在内容变化时写 DOM（沿用现有 `lastTimeText` 那套节流写法）。

**C7.5 `dock-size` / `skin-state` 的到达顺序**

两者可能任意先后到达，实现必须幂等：`dock-size` → 存几何 + `applyDockSize()`；`skin-state` → 存 state + `applyShape(state.shape)`；`applyShape` 内部再调一次 `applyDockSize()`。`dockLayoutSkin` 的视口改为**读当前卡片尺寸**（`cardW/cardH`），不再写死 `116×50`。

**C7.6 点击热区按造型收敛**

`dock.html:585-589` 的 `isInCard(x, y)` 现在用 `#card` 的矩形判定。非 rect 造型的卡片盒四周有 12px 透明内边距（已天然排除），但**圆形造型的四个角**仍是透明区，若不处理会出现「点圆外面的角也弹日历」（v1.7.21 用户报过同类问题）。

- `ring` / `toon`：改用**圆形判定**（圆心 = 卡片盒中心，半径 = `min(cardW, cardH) / 2 - 2`）。
- 其余造型（含 `rect`）：保持矩形判定（现状）。
- 判定函数只替换几何部分，`updateHit` / `setPointerCapture` / `resetHit` / 拖动那套逻辑**一律不动**。

**C7.7 数据来源**

`dock.html` 的造型权威来源是 `skin-state` 里的 `resolved.dock.shape`（即 C3 的 resolve 结果），**不是** `skin.surfaces.dock.shape`。渲染层不得自行判断 follow。

### C8 · 「浮窗样式」入口（`skin.html` 第三个入口）
