## §1 已查明事实（lead 亲自读码核实，非转述）

### 1.1 X1 的真正成因：`template.html` 的 `body` 不透明（**原「系统投影」假设已被实测排除**）
- ❌ **假设被推翻**：我曾把 `electron-main.js:1170` `const HAS_SHADOW = true;` 列为头号嫌疑（它经 `winBase()` 作用于全部 10 个窗口；Windows DWM 系统投影跟随**矩形包围盒**、不跟随内容圆角，听起来严丝合缝）。
  **w-f-frame 的屏幕级 A/B 实测证明它是 0 差异**：`hasShadow: true → false`，主窗四角四片区域在 ±6 / ±20 / ±40 三种半径下**逐像素完全相同**（无差异像素数 0）。⇒ 本机透明无边框窗下 `hasShadow` **根本不绘制任何东西**，X1 与系统投影**无关**。
  ⇒ **`HAS_SHADOW` 保持 `true` 不动**，也不做「按窗口传参」的改造。
- ✅ **真成因**（我独立审计全部 11 个渲染页的 `body` 背景后定论）：

| 文件 | `body` 背景 | 判定 |
|---|---|---|
| **`template.html:696-706`** / **`calendar.html:696-706`** | **不透明浅色渐变** | ❌ **唯一元凶** |
| `template.html:707-709` | `[data-theme="dark"] body` 不透明深色渐变 | ❌ 同源 |
| `dock.html:440-446` | `background: transparent` | ✅ 已干净 |
| `exit.html:123-130` / `holidayupd.html:134-141` / `reminder.html:143-150` / `remindlist.html:128-133` | `background: transparent` | ✅ 已干净 |

| `使用说明.html:24` | `background: var(--paper)` | ⚪ 非 Electron 窗口，不透明是对的 |

- ⇒ **只有 `template.html` 一家有问题**，而它经 `build.js` 生成的 `calendar.html` **同时服务「主窗 mini / 放大 max / 桌面插件 desktop-mode」三态** ⇒ 完美解释用户说的「**所有**窗口圆角外都是直角框」（他日常看到的就是这三个）。

- 🚨 **禁止用无头截图或 CDP 截图判断投影/合成器类问题**：本项目上一轮已因无头假阳性误判过一次（见 MEMORY.md）。**必须屏幕级抓图**（Pillow `ImageGrab`）。

### 1.10 X1 的几何定义与落地证据（**纠正一个流传中的错误口径**）

**「直角框」= 圆角缺口，不是 pad 缝。** 二者是不同的几何量，混用会让判据漏检：

| 几何量 | 定义 | 与 pad 的关系 |
|---|---|---|
| **pad 缝** | 卡片盒与窗口边缘之间的缝 | 左/右 = `padL`/`padR`，上/下 = `padT`/`padB` |
| **圆角缺口** | 窗口矩形 **4 个角**被卡片**圆角**切掉的小三角 | **与 pad 无关**：pad 全为 0 时依然存在 |

- 🚨 **判决性证据**：w-f-frame 实测 desktop 窗口 `340×370` == `#widget` `340×370`（**pad 缝全 0**），按「pad 缝」判据**根本不成框**；但改前四角照采样到 body 渐变板 `[233,237,242]`，改后变壁纸色 `[0,165,242]`。
  ⇒ **「窗口 == 卡片」时依然有直角框**。任何只看 pad 的判据都会漏掉用户亲眼看到的问题（w-a-dock 的首版判定式正是如此，已当面对齐）。
- 由 `dockGeometry` 反推：`rect` 的 `padR`/`padB` = 0 ⇒ 它只可能有上/左两条 pad 缝，**pad 缝判定式对 rect 天然不适用**；而圆角缺口对六款**都成立**。

**X1 的正面收益：从「假不透明底板」换成「真毛玻璃」。**

- `template.html:729` `#widget { background: var(--paper) }`，`--paper` = `rgba(252,251,249,0.84)`（暗色 `:206` = `rgba(28,32,44,0.88)`）
  ⇒ 卡片**本来**就是半透明纸 + `backdrop-filter: blur()`。
- 改前它背后垫的是 body 的**不透明**渐变板 ⇒ 那层 blur 模糊的是一块**死板**，毛玻璃**等于没生效**。
- 改后背后是真壁纸 ⇒ 毛玻璃**第一次真正生效**。
- ⚠️ 因此 **X1 不是「损失浮起感」**：`#widget` 的 `--e-4` 外投影被窗口边界硬切 —— 这是**改前改后都成立**的事实（窗口 == 卡片，没有余量留给投影）⇒ 所谓「浮起感」从来不存在，**不是 X1 引入的回归**。

### 1.11 X4 真机事实（w-f-frame 实测 2026-09-11；**替换此前所有基于推算的模型**）

**① 窗口尺寸被 Windows/Electron 吸附到偶数。**
- 实测 vs 预测：`round(88×0.8)=70` ✓（偶）；`round(88×0.6)=53` → 实测 **54**；`round(88×1.6)=141` → 实测 **142**；`round(174×0.8)=139` → 实测 **140**。
- ⇒ **今后预测窗口 DIP 的口径 = `round(base×s)` 后判奇偶、奇数抬偶**；预测与实测差 1px 且形态为「奇数→偶数」时**不得报红灯**。
- 方向性：吸附**只让 pad 缝变大、不会变小** ⇒ 对 X2 的「阴影必须收进 pad」是**安全方向**。

**② 缝隙尺定律 `gap(物理px) = pad × s × scr`（实测成立）。**
- pixel 下缝实测 **13.0 / 14.0 / 31.0** 物理 px（s=0.6/0.8/1.6），理论 `pad×s×scr` = 10.8 / 14.4 / 28.8；另组测得 11.0 / 14.0 / 29.0，差值 +0.2 归洋红抗锯齿。
- ⇒ 同时确认 `scaleinv` 静态模型与 w-a-dock 的「尺度不变性」两条**独立推算都与真机一致**。

**③ X4 的 S1 不变量首次在真机成立（pixel 造型）。**
- `dpr` 实测 **0.9 / 1.2 / 2.4**（s=0.6/0.8/1.6，副屏 `scr=1.5`）⇒ `dpr = scr × s` 逐位吻合 ⇒ **`setZoomFactor` 确实施加了**。
- 窗口 DIP **108×54 / 144×70 / 288×142**（= base 180×88 × s，含偶数吸附）；**CSS 视口恒 ≈180×88**（实测 180×90 / 180×87 / 180×88）⇒「窗口 DIP = 基础×s + zoom=s ⇒ **渲染层零改动**」成立。
- ring 侧（`report-A.json`）：窗口 DIP 174 / **104** / **278** = `round(174×s)`；CSS 视口 174 / 173 / 174；卡片 DOM **恒 150×150**；窗口位置 **恒 200,200**；`follow` 前后都 = `calendar`。

**④ 方框判据（窗口最外 1~2 物理 px 的 base↔noShadow 差 = 硬切标志），阈值 ≤8/255（3%）**

| 用例 | 最外 1px maxΔ | 2px 带 >25 级 | 判定 |
|---|---|---|---|
| pixel **pre-X2** `0 6px 16px` s=1（**基线**） | **24** | **182 px** | ❌ 硬切 |
| pixel s=0.6 / 0.8（最紧点）/ 1.6 | 0 / 2 / 0 | 0 / 0 / 0 | ✅ 无框 |
| ring s=0.6 / 0.8 / 1.6 | 0 | 0 | ✅ 无框（无外投影） |

- **基线对照是本条的说服力所在**：同一套方法测 pre-X2 得 24 与 182px 超 25 级 ⇒ post 的 0~2 **不是测量噪声**；剖面单调衰减（越靠卡片越强），pre 在窗口边仍 −24 被截断、post 衰减到 −2 完成。

**⑤ 环境事实（供后人，避免重复踩坑）**
- `DevicePixelRatio = 屏幕缩放 × zoom` ⇒ **不能**拿 dpr 当屏幕缩放换算窗口坐标，须 `scr = dpr / s`。
- 本环境 **`tr` 不存在**（用它会把参数静默传空）；`WMIC` 被安全策略硬拦。
- 真实 `settings.json` 取证必须**前后 sha1 一致**（w-f-frame 本轮做到）；抓图/联调一律走隔离 profile。
- ⚠️ **置顶白底板在本机无法用于抓 dock**：`zt.js` 四组对照显示，置顶底板会把**所有**应用窗口（含置顶的日历与 dock）一起盖住，屏幕上只剩任务栏 40px；且借产品自带 `settingsSet('dockPinned')` 把 dock 重新置顶**对像素零影响**（Z4 与 Z3 计数完全相同 76212）。**可用口径 = 非置顶底板 + 在 app 启动之后显示 + 每 1.5s 在普通层内 `moveTop()` 自保不被宿主顶掉。**

### X2（R2）圆环外围不得出现明显方形黑框 —— **成因已定，规格冻结**
**成因**：`dock.html:769`（X2 修复后此处已是「删除外投影」的说明注释）的 ring `--dock-shadow` 外层是 `0 10px 30px rgba(0,0,0,.42)`，可见范围 ≈ `offset + blur = 40px`，而该造型的 `pad` 只有 **12px** ⇒ 被窗口矩形**硬裁一刀**，残留在四角 ⇒ 「明显方形黑框」。
对照组完全吻合：`flip`/`toon` 走 `invisibleCardVars()`（`:717-725`）`--dock-shadow: none` ⇒ 无框；用户也正好主动夸「绘本台钟就很好」。

**全造型算术审计（外投影 `offset + blur` vs 该造型 `pad`）**：

| 造型 | 窗口 | 卡片 | pad | 外投影 | offset+blur | 越界 |
|---|---|---|---|---|---|---|
| **ring** | 174×174 | 150×150 | 12 | `0 10px 30px` | **40** | **+28** ← 最严重 |
| **pixel** | 180×88 | 156×64 | 12 | `0 6px 16px` | **22** | **+10** |
| rainbow | 140×68 | 116×44 | 12 | 只有 inset | 0 | ✅ |
| flip / toon | — | — | 12 | `none` | 0 | ✅ |
| rect | 116×H | 114×(H−2) | L2 T2 R0 B0 | 主题默认外投影 | — | 贴屏角，**刻意接受** |

**改法**（`dock.html`）：
1. **ring**（`:754-755`）：**删除外投影那一层**，保留两道 inset 高光 —— `inset 0 1px 0 rgba(255,255,255,.42), inset 0 0 0 1px rgba(255,255,255,.20)`。依据用户原话「要么**透明**要么渐变消散」。
2. **pixel**（`:736-737`）：**把外投影收进 pad 之内**（`offset + blur ≤ 12`），如 `0 3px 8px rgba(0,0,0,.38)`（3+8=11 ✓）—— 保留机身立体感，只消除硬裁。
3. **补文件头硬约束**：*非 rect 造型的外投影 `offset + blur` 必须 ≤ 该造型 `pad`（当前 12px）*，否则会被窗口矩形硬裁出可见直角边。
- ❌ 不动 `--dock-bg/edge/radius/overflow/blur/sat`（圆盘本体与材质）、不动 `.halo`（`:523-527`，那是**文字**描边）、不动 `rainbow`/`flip`/`toon`/`rect`。

#### X4.1 持久化与归一化
- **`skin.dockScale`，与 `skin.opacity` 并列**（`:1150` 附近），**不放进 `surfaces.dock.*`**（依据 §1.3：跟随态 `resolveSurfaceConfig` 返回 `surfaces.calendar`，存进去会被静默吞掉）。

- 新函数 `normDockScale(v)`（放在 `normShape` `:1231-1233` 之后）：
```js
function normDockScale(v) {
  if (typeof v !== 'number' && typeof v !== 'string') return 1;   // null/undefined/对象/布尔 → 默认
  if (v === '') return 1;
  var n = Number(v);
  if (!isFinite(n)) return 1;                                     // 'abc' / NaN → 默认
  n = Math.round(n * 20) / 20;                                    // 吸附到 5% 档
  if (n < 0.6) n = 0.6;
  if (n > 1.6) n = 1.6;
  return n;
}
```
  - **只依赖 `Math`/`Number`，不引用任何顶层变量** ⇒ 满足 §1.4 式孤立 eval 约束（与 `normShape` 同款口径）。
  - 判据表（交 QA，见 §5 §A）：`undefined`/`null`/`{}`/`true`/`''`/`'abc'` → **1**；`0`/`0.5` → **0.6**（越界夹到下限）；`2`/`99` → **1.6**；`1.234` → **1.25**；`'1.5'` → **1.5**；`0.975` → **1**。
- 归一化落点**两处**（缺一则老用户/新用户各有一条路径拿不到字段）：
  - `normalizeSkinV3`（`:503-519`）末尾加 `out.dockScale = normDockScale(raw && raw.dockScale);`
  - `migrateSkinV2toV3`（`:534-581`）末尾加 `out.dockScale = normDockScale(src && src.dockScale);`（注意局部变量名是 `src`）

```js
var geo = dockGeometry(resolveSurfaceConfig('dock').shape);
var s = normDockScale(skin && skin.dockScale);
dockW = Math.round(geo.winW * s);
dockH = Math.round(geo.winH * s);
if (dockWin && !dockWin.isDestroyed()) {

  if (cur.width !== dockW || cur.height !== dockH) {
```

## §6 明确不做

### 关键推理：为什么 rainbow 可以归零右下 pad，而 X2 的裁切问题不会回来

X2（圆环外投影被窗口矩形硬裁出直角边）的**唯一成因**是「外投影越出 pad 空间」。`rainbow` 的 `--dock-shadow` **两档全是 `inset`**，
**没有任何外投影** ⇒ `padR = padB = 0` 时窗口矩形上没有任何东西需要被裁 ⇒ X2 的成因**对 rainbow 不成立**。
（`ring` 已在 X2 中把外投影整层删除、`pixel` 已把投影收进 12px，同样满足「外投影 ≤ pad」；
`flip`/`toon` 本来无越界外投影。故本轮**只动 rainbow**，其余五款一字不改。）

### 冻结改动（三条，缺一不可）

1. **`electron-main.js` 的 `DOCK_SHAPES.rainbow`** 改为：
   ```js
   rainbow: { name: '虹彩流光', winW: 140, winH: 68,  hMode: 'fixed',   padL: 24, padT: 24, padR: 0,  padB: 0  },
   ```
   为什么是 24/24/0/0 而不是 0/0/0/0：**卡片尺寸必须保持 116×44 不变**。
   `cardW = winW − padL − padR = 140 − 24 − 0 = 116`、`cardH = winH − padT − padB = 68 − 24 − 0 = 44`，
   与文档/测试已冻结的「虹彩流光 116×44」逐字相等；`winW/H` 不动 ⇒ 既有窗口尺寸断言也不破。
   多出来的左上各 24px 是**纯透明区**（彩虹无外投影，不画任何东西），`#card` 的右/下边贴死窗口右/下边。

2. **`electron-main.js` 的 `positionDock()`**：`rainbow` 改为与 `rect` 共用同一分支（**贴工作区右沿 + 压任务栏上沿**）。
   即把 `if (sh === 'rect')` 改为「`rect` 或 `rainbow`」走贴边分支；`pixel`/`ring`/`flip`/`toon` 仍走内缩 24px 分支。
   ⚠️ 不许引入新顶层变量参与 `dockGeometry`（§1.4 孤立 eval 硬约束）；`positionDock` 不受该约束，但改动应保持最小。

3. **`dock.html` 文件头那条硬约束订正**（`:40-42`）：现文写「非 rect 造型的外投影 offset + blur 必须 ≤ 该造型的 pad（注册表统一 12px）」——
   该「统一 12px」在 Y1 后**不再成立**。改为按造型列 pad，并写明 rainbow 的右下 pad 为 0、因它的阴影全为 inset 故无裁切风险。

### Y1 验收标准

- `dockGeometry('rainbow')` ≡ `{ key:'rainbow', winW:140, winH:68, padL:24, padT:24, padR:0, padB:0, cardW:116, cardH:44 }`
- 无 `dockBounds` 的默认启动 + `shape='rainbow'` ⇒ 窗口落点公式与 `rect` **同一条**：
  `x = round(wa.x + wa.width − dockW)`、`y = round(wa.y + wa.height − dockH)`
- 真机：rainbow 卡片盒的**右边缘**与工作区右沿之间、**下边缘**与任务栏上沿之间的**物理像素缝隙 = 0**
- 回归：`pixel`/`ring`/`flip`/`toon` 四款落点与 pad **一字不变**；`rect` 一字不变
